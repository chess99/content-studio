# 技术教程

## 读者任务

让读者能够复现一项操作、理解一套实现，或诊断一类故障。先确定文章更偏向哪一个任务，其他内容为它服务。

## 取材

- 记录环境、版本、输入、前置条件和可见结果。
- 优先使用可复现实验、源码、官方文档、日志和真实失败记录。
- 样本用于证明或解释通用方法。样本自身的业务细节只在影响技术判断时展开。
- 术语、字段名和统计口径必须精确。相近概念不能为了好读而混称。

## 组织

按实际依赖顺序展开。尽早说清完成后会得到什么、需要什么条件、最容易卡在哪里。常用推进关系包括识别信号、准备环境、执行操作、验证结果、处理失败和说明边界；只保留当前任务需要的部分。

原理放在读者需要据此处理变化的位置。一个样本得到的结论不能直接扩大成所有版本、平台或实现的规律。

## 硬要求

- 命令、配置和代码应当可运行，包含必要 import、参数、上下文和调用方式。伪代码必须明确标注。
- 每个关键步骤同时给出动作、预期结果和失败时的检查方向。
- 数字说明统计对象与口径。技术名词沿用真实 API、文件格式或工具字段，不能为了顺口把结构字段和工具计数改写成近义概念。例如 method ID 不等于方法实现数，class definition 不等于反编译器生成的源码文件数。
- 结果需要交叉验证，不能只凭文件大小、单个字符串命中或工具“成功”提示下结论。
- 明确方法的适用条件、没有覆盖的变体和已知失效路径。

关系图、流程图或表格只在多组件关系、重复字段比较或长依赖链用文字难以看清时使用。

## 人称与语气

默认直接陈述问题、证据和操作。第一人称适合说明真实实验动作、失败经历或判断来源，不用它给每个章节加个人复盘标题。第二人称只在操作指令确实更自然时使用。

## 审校重点

- 读者能否从文中判断自己卡在哪一步。
- 代码与命令是否真的覆盖正文承诺。
- 样本是否服务通用方法，而非把无关业务分析带进文章。
- 是否把反编译输出、日志或工具字段解释成了它们并不代表的东西。
